# Tasks: CFDI Payment Receipts (REP)

**Input**: Design documents from `specs/074-cfdi-payment-receipts/`

**Prerequisites**: plan.md, spec.md, research.md (R1–R15), data-model.md, contracts/ui-contracts.md (C34–C44), wireframes.md, quickstart.md

**Tests**: The spec doesn't ask for a test suite as such, but the constitution's quality gates and research R15 require tests. Test tasks sit inside each story, after the code they cover.

**Organization**: Grouped by user story (US1–US5, spec.md). US1, US3 and US4 are P1 and together are the MVP: issue a receipt from a payment, fill it, seal and stamp it. US2 (by hand) and US5 (navigation) are P2. Phase 2 holds what two or more stories share, including the receipt's read-only rendering, so every story's draft opens with its data.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: parallelizable (different files, no dependency on an incomplete task)
- **[Story]**: US1 from a customer payment · US2 by hand · US3 fill payment and invoices · US4 seal, stamp, reopen · US5 navigate

## Cross-story notes

- **Specs 066, 072 and 073 are the base.** Everything is in `lib/features/invoicing` (paths are relative to the repo root) except one button in `lib/features/sales/presentation/payments/payment_detail_screen.dart`. Mirror what 073 did for credit notes: `showIssueCreditNoteDialog` in `presentation/invoice_action_dialogs.dart`, `createCreditNote` and `copyInvoiceLines` in `presentation/fiscal_document_actions.dart`, the credit-note gates in `presentation/fiscal_document_detail_screen.dart`, and credit-note mode in `presentation/invoice_header_dialog.dart`.
- **Generated client.** The operations are `createPaymentReceiptApiV1FiscalDocumentsPaymentReceiptsPost` (body `PaymentReceiptCreate {customer, recipient, customerPayment?}`), `addPaidInvoiceApiV1FiscalDocumentsFiscalDocumentIdPaidInvoicesPost` (body `PaidInvoiceAdd {invoice, amount?}`), `updatePaidInvoice…PaidInvoicesRelationIdPut` (body `PaidInvoiceUpdate {amount}`) and `removePaidInvoice…PaidInvoicesRelationIdDelete`, all in `lib/generated/openapi/lib/src/api/fiscal_documents_api.dart`. The `amount` fields are wrapped types (`Amount3`, `Amount4`, like `Quantity4` in `copyInvoiceLine`): read `lib/generated/openapi/doc/Amount3.md` and `Amount4.md` and build them the way `fiscal_document_repository_impl.dart` builds `Quantity4`. `InvoiceUpdate` already has `paymentDate`, `paymentAmount` (`PaymentAmount`, same wrapper style), `paymentReference` and `orderingBank`. `FiscalDocumentResponse` has `paymentDate`, `paymentAmount`, `paymentReference`, `customerPayment` and `paidInvoices`. No client regeneration is needed.
- **Type codes.** `typeCode == 200` is a payment receipt; `0` is an invoice. The receipt's one write route is the header `PUT`, which accepts only `payment_date`, `payment_amount`, `payment_method`, `payment_reference`, `ordering_bank`, `issued`, `comment` (anything else is `field_not_for_type`).
- **Shared files.** Do these sequentially, not in parallel:
  - `lib/features/invoicing/presentation/fiscal_document_detail_screen.dart`: T009 (foundation), T016 (US1 banner), T018 (US3), T022 (US4) and T028 (US5) each may touch it. Every control is a nullable callback or a condition, so an absent right or state means the control is not in the tree.
  - `lib/features/invoicing/presentation/new_invoice_dialog.dart`: T012 (US1) refactors it; T025 (US2) only calls it.
  - `lib/features/invoicing/presentation/invoice_header_dialog.dart`: T019 (US3) only.
  - `lib/l10n/app_en.arb` and `lib/l10n/app_es.arb`: T002 adds every key once. If a later task needs another, add it there and run `flutter gen-l10n`. Never hand-edit `lib/l10n/app_localizations*.dart`.
- **Generated code.** After editing a freezed or `riverpod` file, run `dart run build_runner build --delete-conflicting-outputs` at the repo root, then revert `delivery_orders_filter.freezed.dart` if it changed (stale committed file). Never run two build_runner processes at once.
- **Formatting.** Format only the files you changed (`dart format <files>`). Never `dart format .`, and never format `lib/generated/`.
- **Dates and amounts** go through `formattersProvider` (§V). Spacing comes from `Theme.of(context).spacing`, colours from `ColorScheme`. No hex values.
- **Never match server prose** (§III). Refusals are shown through `FiscalDocumentRefusal` / `AppError.localizedMessage`, built from the error's `code` and `params` (`error.problem?.code`, `error.problem?.intParam('fiscal_document_id')`). Recognition keys on the code.
- **Never compute installments or balances client-side** (research R4). Only the unassigned difference (payment amount less the sum of the paid amounts) is computed here, from server values.
- **Refusal widget.** The existing create dialog shows refusals with `FiscalDocumentRefusal` (not a bare `FormErrorBanner`); the new dialogs do the same. Contract C35/C41's "FormErrorBanner" means that banner as `FiscalDocumentRefusal` renders it.
- **Rights.** Create needs 23 create; edits need 23 update; the source-payment link needs 8 read (`SystemObject.customerPayments`). A missing right means the control is absent, never disabled.
- **Simplifications.** Any shortcut carries a comment `// simplified: <ceiling>, <what to do when it binds>`.
- **Companion hooks are not used** for this spec (plain speckit).

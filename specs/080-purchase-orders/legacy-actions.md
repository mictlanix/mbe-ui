# Legacy action accounting (SC-006)

Sources: mictlanix/mbe-roadmap#71 ("Weight: 17 legacy actions"), the legacy `mbe` repo's `docs/specs/05-purchases.md` §3–4 and its controller `Web/Controllers/Mvc/PurchasesController.cs`, and mbe-api's `docs/specs/05-purchases.md` §3–4 for what the new API changed on purpose. The controller has 28 distinct public action names (GET/POST overloads of one name counted once). Neither the roadmap nor either docs folder records how the weight of 17 was derived, so this file reconstructs it with one rule: **one row per user-facing function**. That rule merges the six per-field line editors into one row (−5), merges `View` into `Details` (same read-only view, −1) and `Print` into `Pdf` (same document as HTML or PDF, −1), and leaves out the four endpoints that only re-render a fragment of the edit page after an AJAX call (−4): 28 − 11 = 17. The legacy doc's "Receive" action is not a controller action (it navigates to Inventory → Receipts) and "Email" has no legacy endpoint; both are noted in rows 14 and 16.

| # | Legacy action | What it did | Status in spec 080 |
|---|---------------|-------------|--------------------|
| 1 | `Purchases.Index` (GET, POST) | List orders the user created or updated, not cancelled; search by number, supplier or warehouse; `*` shows everyone's. | Covered: FR-004, FR-005, FR-006 (scope switch replaces `*`; filters by state, supplier, creator, dates) — T017, T023. |
| 2 | `Purchases.Approvals` (GET, POST) | Queue of completed, unapproved orders, searchable by supplier or creator. | Dropped: no purchase order approval (mbe-api 05 §4: used only 2024-11 to 2025-03, off since Mar 2025, decided 26 Oct 2026). |
| 3 | `Purchases.Approve` (GET, POST) | Approve or reject an order; on approve with approval on, generate its inventory receipts. | Dropped: same as row 2. The receipt generation moved to confirm (row 14). |
| 4 | `Purchases.Details`, `Purchases.View` | Read-only view of an order (where completed or cancelled orders land). | Covered: FR-012, FR-016, FR-020, FR-025 — T013. |
| 5 | `Purchases.Create` (GET, POST) | New order by hand: choose the supplier (and notes). | Covered: FR-010 (supplier, optional date and notes) — T016. |
| 6 | `Purchases.ToPurchaseBySupplier` | Pending request lines grouped by supplier, with line count and total at cost. | Covered: FR-007, FR-031 (groups now per supplier and destination facility; "Sin proveedor" group shown) — T011, T014. |
| 7 | `Purchases.CreatePurchaseBySupplier` | One click creates a draft order from every pending line of a supplier (optionally one warehouse), priced from cost. | Covered: FR-008, FR-009, FR-018 (per supplier and facility, left-out lines counted) — T008, T014. |
| 8 | `Purchases.Edit` (GET, POST) | Edit the draft's header: supplier and notes. | Covered: FR-011 — T030, T033. |
| 9 | `Purchases.SetEstimatedReceiptDate` | Set the estimated receipt date on a draft, refusing dates in the past. | Covered: FR-010 (at create), FR-011 (on a draft, not in the past) — T016, T030, T033. |
| 10 | `Purchases.AddPurchaseDetail` | Add a product line: quantity 1, cost as price, product's tax rate. | Covered: FR-013, FR-014, FR-015 (defaults from the server, including the user's point-of-sale warehouse) — T019, T022. |
| 11 | `Purchases.AddFromPurchaseRequest` | Add the pending lines of one request by folio, or with `*` every pending line of the order's supplier across requests. | Covered: FR-017, FR-018 (one approved request at a time) — T020, T022. The `*` all-requests form has no API route; Por comprar (row 7) covers that need. |
| 12 | `Purchases.EditDetailQuantity`, `EditDetailPrice`, `SetItemTaxRate`, `EditDetailWarehouse`, `EditDetailDiscount`, `EditDetailCurrency` | Inline edit of one line field each. | Covered for quantity, price, tax rate and warehouse: FR-013, FR-015 — T031, T033. Discount and currency dropped: the API fixes discount 0, MXN, rate 1 and tax-included off (mbe-api 05 §3 line fields), so FR-020 hides them. |
| 13 | `Purchases.RemoveDetail` | Delete a line. | Covered: FR-013 — T032, T033. |
| 14 | `Purchases.Confirm` | Complete the order, raise the cost list to the order price when higher, and (approval off) generate one inventory receipt per warehouse. | Covered: FR-021, FR-022, FR-023 — T021, T022, T024. The server now creates the receipts on confirm; cost changes moved to receipt confirmation as a weighted average (mbe-api 05 §3 Average Cost), which the UI does not show (cost-change history out of scope per the spec's Assumptions). Legacy "Receive" is the link to each receipt (FR-022). |
| 15 | `Purchases.Cancel` | Cancel a draft and delete its request-linked lines so the request lines become pending again. | Covered: FR-024, FR-025 — T032, T033. The API now keeps the lines as history and frees their request lines. |
| 16 | `Purchases.Pdf`, `Purchases.Print` | Print the order as PDF or HTML; a draft printed as a "quotation". | Covered for confirmed orders: FR-026 — T026, T029. Draft (quotation) printing dropped: the API prints only confirmed orders (mbe-api 05 §3 Print and Email). Email is new, no legacy endpoint: FR-027, FR-028 — T027, T028, T029. |
| 17 | `Purchases.Export` (POST) | Download a draft as an Excel "purchase quotation" (`.xls`) to send to a supplier. | Deferred: requested from the server as a draft quotation document (mictlanix/mbe-api#356), UI follow-up mictlanix/mbe-ui#310. |

Not counted, AJAX fragment helpers of the legacy edit page (no user function of their own; the Flutter screens rebuild from state after each write): `Purchases.DiscardChanges` (re-render the header view), `Purchases.GetTotals`, `Purchases.GetDetail`, `Purchases.GetDetails` (re-render totals or changed lines).

## Unresolved

None. **`Purchases.Export`** (a draft exported as an Excel purchase quotation) was decided on 2026-11-28: spec 080 ships without it, and the quotation is requested from the server as a draft document in mictlanix/mbe-api#356, with the UI follow-up in mictlanix/mbe-ui#310.
